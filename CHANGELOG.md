# Changelog

## 0.91.8
- **Pull Env reads a site's values through the reveal, after a person approves.** "Hiveku: Pull Env to .env.local" now asks Hiveku for the development values the site runs with. Hiveku asks a person first: the extension opens the approval page (anyone in the account who can see the site's variables can approve, you included) and writes `.env.local` as soon as it lands, waiting up to 10 minutes. Sensitive variables and platform credentials are never written; their names are listed in the file as comments with the reason. The file is readable by you only, also when it replaces an older one, and nothing is written when no value came back.
- **Values keep their exact text.** A multi-line value (a private key, a JSON credential), a `$`, quotes or a `#` are written so Next.js, Vite and Expo read them back exactly.
- **Push Env saves development values only.** It stores what is in `.env.local` for development (as `KEY_DEV`), so it can never change staging or production. Keys named for staging or production are left out.
- **Secrets lists show names, never values.** The Secrets section, "Manage Secrets" and the project's env document list each variable with where it reaches and whether it is sensitive. The env document is read-only: change a value with "Manage Secrets", which now asks which tier it is for, or in the dashboard.
- **Claude Code in your project folders tells Hiveku it asks before a reveal.** The `.mcp.json` the extension writes says so with its version, because the folder's settings ask before every `project_secrets_reveal`. Hiveku then lets a reveal through after that prompt instead of also asking in the dashboard. Folders you already have pick this up on "Hiveku: Refresh Setup"; until then their reveals take the dashboard approval.

## 0.90.0
- **A pull request refused for conflicts can be settled.** Merging a pull request whose files conflict used to say "Resolve them on <branch>, save a version, then merge again", which never worked: the merge compares against where the branch started, so the file still conflicted. Now the message names the files and offers:
  - **Resolve in the dashboard** opens that pull request's review on the Hiveku dashboard, where each file can keep the branch's version, use Your site's, or get new text.
  - **Resolve here** lists the conflicting files one at a time. For each, keep the branch's version, use the other side's, compare the two first, or leave it for the dashboard. After a confirmation that lists your choices, it saves one version on the branch. Your site changes only when the pull request merges, and **Merge again** follows.
- **Sites that require an approval.** When a site's "Require an approval" rule is on, a merge that nobody has approved yet, or whose changes moved after the approval, says so in Hiveku's words with **Open in the dashboard**, where people approve. A draft says to mark it ready first. A direct Merge into Your site on such a site offers **Open a pull request** instead. The Pull Requests list says when a pull request still needs an approval or is a draft, and has **Open in the dashboard** for its comments, reviews and approval.
- **Merged branches are archived.** When a pull request merges, Hiveku archives its branch: hidden from the branch list, closed to changes, and restorable for 30 days before it is deleted. After a merge VS Code says so, and offers to switch to the target branch when this folder is on the archived one, instead of offering to delete it. Saving to an archived branch, or any other change to it, offers **Restore branch**.
- **Claude Code in your project folders knows the new steps.** `/hiveku-pr` reads a pull request's reviews and comments, posts a review that comments or asks for changes (it never approves: people approve in the dashboard), and settles conflicts file by file with you. `/hiveku-branch` lists and restores archived branches. Reading reviews, comments, conflicts and the approval setting no longer asks for permission. Settling conflicts always asks, in every permission mode. Folders you already have get that ask rule when VS Code starts; the new commands and the read rules come with "Hiveku: Refresh Setup".
- **Pull requests show their own changes.** "Review files" and the change counts now list only what the pull request itself changed since its branch started. Before, they also counted what Your site changed after the branch started, as if the pull request had made those changes.
- **You see conflicts before you merge.** In the Pull Requests list, a pull request that conflicts with the branch it goes into says so, and one that would conflict with other open pull requests names them ("conflicts with #3 and #5"). The Merge choice says how many files conflict with Your site, or which pull request it collides with once one of them merges. `/hiveku-pr` reviews from the pull request's own changes and reads whether it merges cleanly before asking you to merge: which pull request should go first, and that the second will need its conflicts settled after the first merges.

## 0.85.6
- **Downloads and command sync stay inside the account folder.** The knowledge download used an entry's stored department as a folder name exactly as stored, so a malformed department could make the next download write a file outside the account folder on your machine. A department is now used only when it is a plain lowercase name; anything else is filed under `general` (the entry is still downloaded, only its folder changes), and every file the download and the command sync write is checked to land inside the folder first. Command sync also never deletes a file outside the folder because of a row in its manifest.
- **Commands survive a department changing case.** Content tags are now lowercased, as the Claude Code plugin already did. On a case-insensitive disk (the macOS default), the first sync after the upgrade used to see the old capitalised command name as removed upstream and delete the file it had just kept under the new name. The sync now recognises that both names are the same file and keeps it.
- **Safe on Windows.** Names Windows reserves for devices (`con`, `nul`, `com1` and the like) are never used as a folder or file name: a department with such a name files under `general`, and an entry whose file would get such a name is saved as `<name>-entry.md`.

The default is now the edge ceiling rather than 60s, which stays true without anyone maintaining a table across ~2,000 tools. The known-slow overrides remain as documentation, clamped on read.
- **Three live Microsoft Ads writes were auto-approved in every scaffolded folder.** The `*_list_*` glob spans underscores, so alongside the 47 GET readers it exists for it also matched `ppc_bing_shared_negative_list_create`, `_items_add` and `_associate` — tools whose own descriptions say every associated campaign starts blocking those terms immediately. The glob is kept (dropping it would prompt on every CRM and SEO read); the three writes are denied by name, which beats an allow and beats the permission mode. The `check-permission-rules` gate that waved this through while reporting "0 mutations" now scrapes the allow array rather than the whole file, subtracts denials, and treats POST-dispatched reads by name — so the next leak fails the publish instead of shipping.
- **Squarespace, Wix and Shopify sites are labelled as themselves.** The extension's platform union was three behind the builder's, so those resolved to `url` and their tree row read "external". The union and its labels are mirrored from the builder rather than kept as a third copy, and the new-site command teaches the full enum.

- **Pull, diff and discard are branch-aware.** "Pull Latest" on a branch materializes that branch's tree (code only; the main-only snapshot tarball is no longer used there). Clicking a changed file diffs against the branch's copy, and "Discard Changes" restores the branch's copy instead of main's.

- **Commit with nothing local promotes.** On a branch with no local changes but uncommitted edits in its working tree (an agent's push, for example), Commit offers to promote those edits into a commit.
