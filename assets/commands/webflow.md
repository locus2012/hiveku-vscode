---
description: "CRUD an external Webflow site - pages SEO, schema markup, CMS items, assets, custom code, llms.txt - then publish."
argument-hint: "[what to do - e.g. 'fix the SEO titles' or 'install analytics']"
---

Work on one of the account's website projects that is HOSTED ON WEBFLOW$ARGUMENTS. Load `hiveku-web-agency/references/webflow-sites.md` first: it carries the gates as codes, the staged-versus-live model and the Availability table. A Webflow project has no code, no build and no deploy tier; every change is staged on Webflow and goes live on a publish.

1. RESOLVE the project with `sites_list` - the rows with `external_platform: "webflow"` are the Webflow sites; `project_id` is that row's `id`, and `external_website_url` is the live site. Do NOT use `list_projects` / `get_project`: those return pm_projects rows, a different id space, and a website UUID 404s against them. A null `external_platform` on an external row is a plain tracked URL site, not a Webflow site.
2. CONNECTION and auth kind: `webflow_site_get({ project_id })` answers the bound site (`no_webflow_connection` means the panel on the project's Settings page has not been completed; send the user there) and `webflow_token_introspect({ project_id })` answers the granted scopes, the rate limit and whether this is a site token or an OAuth connection. Custom code, the analytics snippet and webhook registration are OAuth-only (`412 oauth_required` on a site token); redirects, robots.txt, well-known files and llms.txt are Enterprise-only (`402 not_enterprise_plan_site` elsewhere). Say which limit applies before promising the work.
3. THE FAMILY the ask needs (every write lands STAGED):
 - Pages SEO: `webflow_page_list({ project_id })` for every page with its SEO fields, then `webflow_page_metadata_update({ project_id, page_id, title?, slug?, seo?, openGraph? })` per page (only the fields passed change). Many pages at once is the bulk metadata write in the reference's Availability table, or the SEO grid's Save all in the workspace.
 - Schema markup and llms.txt: described by capability in the reference (the Schema section and the llms.txt section); the tool names live only in its Availability table. Validate JSON-LD before writing (an object or a `<script type="application/ld+json">` block; 60 KB, 32 levels, 5000 nodes) and treat a `402` on llms.txt as the plan, not a bug.
 - CMS: `webflow_cms_collection_list({ project_id })` then `webflow_cms_collection_get` for the field schema; `webflow_cms_item_create` / `webflow_cms_item_update` (bulk: `webflow_cms_item_create_bulk`, `webflow_cms_item_update_bulk`), then `webflow_cms_item_publish({ project_id, collection_id, item_ids, confirm: true })` to make the items live without republishing the site (it asks first: the items go in front of visitors immediately, and so do `webflow_cms_item_unpublish` and `webflow_cms_item_unpublish_bulk`). The generic `cms_*` tools and `cms_publish` serve the same collections by slug; a content item goes through `content_publish_to_site`, never a second raw write. Deletes have no restore on Webflow - confirm with the exact ids.
 - Assets: `webflow_asset_upload({ project_id, file_name, source_url | project_asset_id, alt_text? })`, `webflow_asset_list`, `webflow_asset_update` for alt text.
 - Custom code and the analytics snippet (OAuth only): check first with the two-read join in the reference (`webflow_script_list` for the `HivekuAnalytics` entry, `webflow_site_customcode_get` for whether that script id is applied; installed = registered AND applied). Only when it is not installed run `webflow_hiveku_snippet_install({ project_id, kind: "analytics", confirm: true })` (it asks first: the loader lands in the header of every page), and name the publish that makes it live. Other scripts: `webflow_site_customcode_get` then `webflow_site_customcode_set` (read-then-merge; it replaces the full applied list and asks first).
 - Redirects and robots (Enterprise): `webflow_redirect_list` / `webflow_redirect_create` / `webflow_redirect_update` / `webflow_redirect_delete`; `webflow_robots_get` then `webflow_robots_update` (merge) rather than `webflow_robots_replace` (removes every rule not sent).
4. PUBLISH after the user's yes: `webflow_site_publish({ project_id, confirm: true })` puts every staged change live on the site's domains (one publish per minute; a `429 publish_cooldown` carries `retry_after_seconds`). Item-only publishes use `webflow_cms_item_publish` and do not need a site publish. Report which copy changed: "saved" is staged, "live" is published, and only after the publish answered. For event-driven work ("every time an item changes", "after each publish", "when a form comes in") use `/hiveku:automate` with the `webflow*Trigger` nodes and the Webflow action nodes (`workflow_node_types_list`, category `webflow`) rather than polling or registering your own webhook: Hiveku already receives the site's webhooks, and the nodes carry the staged-write, confirm and publish-cooldown rules.
5. Finish every session of work the same way: persist notable learnings to department memory - read the department's current document with `memory_list({ domain: "<dept>" })`, append your note to the `content` it returns, and send the WHOLE merged document to `memory_update({ memory_id, content })`, which REPLACES it (sending only the new note destroys everything that department had accumulated); use `memory_create({ type: "memory", name: "<dept>", content })` only when no entry exists, and keep `<dept>` to a canonical department name (see hiveku-orient), and reflect the work in Hiveku PM: `pm_projects_list` to find the project (it filters only by `status`; `project_type` is named in its description but is NOT in its schema, so the proxy drops it and you filter the returned list yourself), or `pm_projects_create({ name, project_type })` where project_type is one of seo | ppc | marketing | website | app_dev, then `pm_tasks_create({ project_id, title })` (the field is `title`, not `name`), `pm_tasks_update` as it moves, `pm_tasks_complete({ id, summary })` when the loop is closed. Reopen a task closed too early with `pm_tasks_uncomplete`, never `pm_tasks_update`. A memory_update that destroyed content is recoverable: `memory_list_versions({ memory_id })` lists the snapshots taken before every PUT or DELETE, and `memory_restore_version({ version_id })` restores one (it works for deleted entries too). Hiveku, not this folder, is the source of truth.
